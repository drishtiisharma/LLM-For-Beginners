# Ollama Raw API Requests: What I Actually Tested

Okay so, after using `ollama run` for a while, I got curious about what’s happening underneath the chat interface.

Turns out, Ollama is basically running a local AI server on your machine. And instead of only chatting through the terminal, you can directly send HTTP API requests to it — just like talking to a backend server.
This was the moment things started feeling less like “using AI” and more like actually understanding how these systems communicate internally.

The two API routes I experimented with the most were:

- `/api/generate`
- `/api/chat`

And honestly, understanding these two explains most of how local LLM apps work.


# The Two Main Ollama APIs

### 1. `/api/generate`

This is the simpler API.

You send:
- a model
- a prompt

And the model generates text back.

It’s basically:
> “Here’s my prompt → give me generated text.”


## First Generate Request (Streaming Response)

Paste this into Git Bash:

```bash
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2:1b",
  "prompt": "Why is the sky blue?"
}'
```

This generates the response **word-by-word** (technically token-by-token). You’ll literally see chunks arriving continuously in the terminal instead of one big final response. It feels similar to how ChatGPT types live while responding.

## What I Understood From This

By default:
- Ollama streams outputs
- The response arrives gradually
- This reduces waiting time
- The model starts replying before generation fully finishes

This made me realize:
LLMs don’t “think everything first and then answer.” They generate text one token at a time in sequence. That’s why streaming feels natural and fast.

## Second Generate Request (Single Full Response)

Now paste this:

```bash
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2:1b",
  "prompt": "Why is the sky blue?",
  "stream": false
}'
```

This disables streaming.

Instead of receiving chunks continuously, you get:
- one complete response
- after generation fully finishes


## What Changes Here?

Now the API returns a full JSON response containing things like:

- model name
- response
- created_at
- total_duration
- eval_duration
- done_reason

Example structure:

```json
{
  "model": "llama3.2:1b",
  "created_at": "...",
  "response": "...",
  "done": true,
  "done_reason": "stop",
  "total_duration": 123456,
  "eval_duration": 98765
}
```


## What I Realized

This is the kind of response developers usually use in applications because:
- it’s easier to parse
- easier to store
- easier to display cleanly in apps


# 2. `/api/chat`

Then I explored the chat API. This one works differently.
Instead of sending:
- one single prompt

You send:
- a list of conversation messages

Which means the model now understands:
- roles
- chat history
- conversational structure

This is much closer to how real chatbot apps work.


## Chat Request Example

Paste this into Git Bash:

```bash
curl http://localhost:11434/api/chat -d '{
  "model": "llama3.2:1b",
  "messages": [
    {
      "role": "user",
      "content": "why is the sky blue?"
    }
  ],
  "stream": false
}'
```

## What This Returns

Instead of a plain `"response"` field, it returns a `"message"` object.
Something like:

```json
{
  "model": "llama3.2:1b",
  "created_at": "...",
  "message": {
    "role": "assistant",
    "content": "..."
  }
}
```

## The Difference Finally Clicked For Me

### `/generate`
Feels like:
> “Complete this text.”

### `/chat`
Feels like:
> “Participate in this conversation.”

That tiny difference changes everything. Most AI chat applications use chat-style formatting internally because conversations need:
- roles
- memory
- structured history
- multi-turn interactions


# What GGUF Actually Is

At first, I kept seeing people say:
> “GGUF uncensored models”

And honestly, it sounded like GGUF itself was some special uncensored AI technology. But that’s not actually true.


## So What Is GGUF?

GGUF is just a file format. That’s it. It’s mainly used for running models locally in tools like:
- Ollama
- llama.cpp

Think of it like:
- `.mp4` for videos
- `.pdf` for documents
- `.gguf` for local AI models

The format itself is not “uncensored.”

## Then Why Do People Associate GGUF With Uncensored Models?

Because local models can be:
- fine-tuned differently
- modified freely
- run without company moderation systems

Unlike cloud AI systems, local models don’t necessarily have strict safety layers added on top.

So people often download:
- uncensored fine-tunes
- roleplay models
- experimental models

And many of those are distributed in GGUF format. That’s why the association exists.
Not because GGUF removes censorship.
But because it’s commonly used for locally runnable models.

# Testing Uncensored Models Locally

After understanding how Ollama APIs work, I got curious about another thing I kept hearing online:

> “uncensored local models”

At first, I assumed this meant:
- illegal models
- hacked models
- or some secret AI versions

But honestly, it’s usually much simpler than that.

Most “uncensored” models are just:
- community fine-tuned models
- with fewer refusal/safety behaviors
- designed for freer conversations, roleplay, or experimental outputs

And because they run locally, there’s no cloud moderation layer sitting between you and the model.


# Downloading an Uncensored GGUF Model From Hugging Face

After understanding how Ollama APIs work, I wanted to try running a community fine-tuned uncensored model locally. Instead of downloading directly from Ollama’s library, this time I explored Hugging Face — because that’s where most GGUF models are shared by the community. And honestly, this was the moment I finally understood how local AI models are actually distributed and used.


## Step 1 — Go to Hugging Face

Open: [Hugging Face Models](https://huggingface.co/models) 
This is basically the biggest public hub for AI models.

People upload:
- base models
- fine-tuned models
- GGUF versions
- roleplay models
- coding models
- uncensored variants
- experimental community models


## Step 2 — Search for a GGUF Model

In the search bar, try searching things like:

```text
dolphin mistral gguf
```

or

```text
openhermes gguf
```

or

```text
uncensored gguf
```

One model I experimented with was:

```text
Dolphin-Mistral-7B-GGUF
```

Usually you’ll find repositories uploaded by people like:
- TheBloke
- bartowski
- QuantFactory

These people often convert models into GGUF format for local use.


## Step 3 — Open the Model Repository

Inside the repository:
- read the description
- check the RAM requirements
- check whether it’s instruction-tuned/chat-tuned
- check whether it’s GGUF format

Then go to the **Files and Versions** section.

You’ll usually see files like:

```text
model.Q4_K_M.gguf
model.Q5_K_M.gguf
model.Q8_0.gguf
```
But they’re mostly just different quantization levels.


## Step 4 — Understanding Which GGUF File To Choose

This part confused me initially.

Smaller quantizations:
- use less RAM
- run faster
- slightly lower quality

Larger quantizations:
- use more RAM
- slower
- better quality

A very common beginner-friendly choice is:

```text
Q4_K_M
```

Because it gives a really good balance between:
- speed
- RAM usage
- quality


## Step 5 — Download the GGUF File

Download the `.gguf` file you want.

Example:

```text
dolphin-mistral-7b.Q4_K_M.gguf
```

This file is basically the actual local AI model.

Depending on the model size, downloads can range from:
- 1 GB
- to 10+ GB


## Step 6 — Create a Modelfile

Now create a folder somewhere on your computer.

Inside it:
- place the `.gguf` file
- create a file named:

```text
Modelfile
```

Inside the `Modelfile`, write:

```text
FROM ./dolphin-mistral-7b.Q4_K_M.gguf
```

This tells Ollama:
> “Use this GGUF model as the base model.”


## Step 7 — Import the Model Into Ollama

Open terminal inside that folder and run:

```bash
ollama create my-uncensored-model -f Modelfile
```

Now Ollama imports the GGUF model and registers it locally under the name:

```text
my-uncensored-model
```

## Step 8 — Run the Model

Now simply start chatting:

```bash
ollama run my-uncensored-model
```

And that’s it.

You’re now running a community GGUF model locally through Ollama.

No cloud API.
No OpenAI servers.
No internet inference.

Everything is happening directly on your machine.


## Step 9 — Experiment With Parameters

This became the fun part. Inside the chat you can experiment with:

```bash
/set parameter temperature 1.2
```

or:

```bash
/set system "You are a creative sci-fi storyteller."
```

And suddenly the same model behaves completely differently.

This made me realize:
LLMs are not just “one personality”. A huge amount of behavior comes from:
- system prompts
- temperature
- fine-tuning
- model size


## One Important Thing I Learned

“Uncensored” does NOT automatically mean:
- smarter
- better
- more accurate

It simply means:
- fewer refusal behaviors
- less filtering
- more freedom in responses

Smaller uncensored models especially can:
- hallucinate heavily
- become chaotic
- confidently generate nonsense

So model quality still matters a LOT.


## Final Understanding

This entire process made local AI feel much more understandable. At first, models felt like mysterious black boxes.

But after manually:
- downloading GGUF files
- importing models
- experimenting with temperatures
- testing APIs
- changing system prompts

I finally started understanding how local LLM ecosystems actually work underneath.
